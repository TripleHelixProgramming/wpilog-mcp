# WPILog Explorer: Looking at the Data Without an Agent

The plan and implementation record for a viewer inside the WPILog Analyzer extension: a way to look at the logs wpilog-mcp reads, for the people who want to see the data themselves. The first half is for anyone on the team; the second half specifies the work for the developers who will build it, in the form [PIT_SERVER_PLAN.md](PIT_SERVER_PLAN.md) uses.

## Part I: The Idea

### What it is

WPILog Analyzer gives an AI assistant the tools to analyze a robot's logs. WPILog Explorer, inside the same extension, gives a person the same view, in the same editor, with no assistant in between. Open a `.wpilog` file in VS Code and it opens as a log: the entries on the left, a plot in the middle, the match phases shaded behind the plot, the statistics of what is on screen beside it, and the robot's console below. Click an entry and it plots; drag across the plot and the statistics follow the selection; type in the console pane and the matching lines appear with their time on the plot.

It is built on the server the extension already bundles, and it calls the same tools the assistant calls. So the number a student reads off the statistics panel is the number the assistant would have reported, computed by the same code from the same file, with the same data quality beside it. A question that starts by looking can continue by asking: a selection becomes a prompt, already naming the file, the entry, and the time window, so nothing has to be retyped. And it needs no assistant to be useful: install the extension, open a log, and look.

It reads REV logs beside the robot's log, on the robot's clock, as the server already synchronizes them. With a pit server on the team's network (see the pit server plan), it lists the team's sessions, follows a live session as it is recorded, and shows which sessions are mirrored on this laptop for the trip home.

### Why

- **Not everyone wants to ask.** A mentor who has read logs for years wants to see the trace, not describe it. A student learning what a brownout looks like learns it from the plot. The analyzer serves the question; the explorer serves the look.
- **Looking and asking belong together.** Today the look happens in another program and the question in VS Code, and the file, the entry, and the time window are carried between them by hand. Here the plot and the prompt share a selection.
- **One set of numbers.** A viewer with its own statistics and its own notion of a match phase disagrees with the assistant in small ways that cost an afternoon. The explorer shows what the server computes, so there is one answer.
- **The code is in the same window.** The log explains the code and the code explains the log, and VS Code already holds the code.
- **The log folder stops being a pile.** A season's logs copied off a robot by hand are a folder of files named by date, from two robots, with the REV logs mixed in. The extension offers to organize them the way the pit server keeps its own: by robot, then by session, with the robot's files beside each other and a manifest that remembers where each came from. The folder reads the same whether a pit server filled it or a person did, and the layout teaches itself.
- **One extension, not two.** A viewer and an analyzer that share a server, a configuration, and a selection belong in one install. A team member with no interest in assistants installs the same extension and uses the viewer; the same server supplies both views and assistant calls.

### What it is not

- **Not AdvantageScope.** No 3D field, no video synchronization, no live connection to the robot of its own, no replay. AdvantageScope is excellent at those and stays the tool for them. The explorer is a log reader that lives where the code and the assistant live, and that shows the assistant's numbers.
- **Not a dashboard.** It reads logs. It does not talk to the robot and cannot change anything on it.
- **Not a second analysis.** It adds no analysis of its own. Every number it shows comes from a tool the assistant can call, and anything it needs that the tools lack is added to the server as a tool, so the assistant gains it too.

### How it works, in one picture

```
 VS Code agents     Explorer (extension host)     Claude Code / Desktop
       |                 |         |                       |
      /mcp              /mcp   /data/entries           connect http
       |                 |         |                       |
       +-----------------+---------+-------- /mcp ----------+
                                   |
                    standalone http server on loopback
                                   |
                  home YAML + clients' directory/key leases
```

The webview draws results supplied by the extension host and opens no network connection. The shared server supplies both tool results and sample streams, so a log loaded for the viewer is loaded for the assistant. A configured pit-server URL supplies a separate HTTP connection, and the local server maintains its offline mirror.

### Where it stands

Milestones 1–8 are implemented: the shared standalone server and session leases; log and entry trees; plotting through the Arrow/CSV data endpoint; console, struct/array fields, and field pose; REV synchronization; organizing stores through import jobs and the inbox; and pit sessions, follow, mirror controls and laptop sync. Automated tests cover pure models, real transport/client integration, and the milestone 11 real-editor smoke. The remaining interactive checks are listed under the milestones and in DEVELOPMENT.md. Notebooks, assistant chart links, and the remaining viewer conveniences are still planned. Pit/mirror interaction in real VS Code remains unverified.

## Part II: Specification

What follows is for the developers. It follows `CLAUDE.md` and the design principles in [ARCHITECTURE.md](ARCHITECTURE.md), and the extension's conventions: TypeScript against the VS Code API, no runtime npm dependencies, logic that needs no VS Code API in pure modules with tests on Node's test runner, and `extension.ts` as the glue.

### 1. Decisions

1. **One extension.** The explorer is part of WPILog Analyzer (`TripleHelixProgramming.wpilog-analyzer`), in `vscode-extension/`, under the same version, build, tests, CI, and release. The Marketplace identifier cannot change without becoming a new listing, so it stays; the display name and the README say that the extension analyzes logs with an assistant and shows them without one. "WPILog Explorer" names the viewer inside it: the custom editor, the views, and their commands.
2. **The webview never touches the network.** The extension host is the client. It starts the shared standalone server and registers the window’s directories by lease; the viewer and assistants reach that server over HTTP. A configured pit server has a separate HTTP client, with no local directory or key lease. The webview receives results and data by `postMessage` (typed arrays travel as transferable buffers, which VS Code passes without copying through JSON) and sends requests the same way. This keeps the server's `Origin` check as it is (a webview's origin is `vscode-webview://<id>`, which the check rightly refuses, while a request from the extension host carries no `Origin` at all), and needs no CORS beyond what exists.
3. **Every number on screen comes from a tool.** The explorer computes no statistic, no phase, no synchronization of its own. What the tools lack is added to the server as a tool, with the tool checklist, the description tests, the conformance sweep, and the differential check, so the assistant can call it too. The first two are `read_entry` at screen resolution and `render_chart` (§6).
4. **One configuration.** The explorer uses the extension’s directory and team settings; those become session leases, shared with the assistants. Permanent server settings stay in `servers.yaml`, which the Settings UI does not edit. Java/heap settings run the installer; the installed launcher controls the daemon. No second set of viewer settings is introduced.
5. **One server per laptop, shared by its clients, on loopback HTTP.** The extension installs or updates the standalone layout from its bundled JAR, starts its `http` server, and publishes one HTTP definition for VS Code’s agents. Claude Code uses a user-scope bridge registration (`claude mcp add --scope user … connect http`), run when its CLI is present and otherwise shown with a copy action. One JVM shares loaded logs and cache; directories distinguish robots/projects, so a server picker and split heaps add no value. A first draft let the user define several servers, each with its directories and team, and let a project name the one it used; it was taken out because a second server on one laptop buys nothing: the server keeps every log apart by path and unloads logs when memory runs short, a tool reads one log per call, and what the draft really offered was a team number per directory, which a directory lease now carries. The private daemon and `useStandaloneServer` setting are retired.

   **Directories by lease, built in milestone 7.** The window registers User and open-project directories with per-path teams, and its secret-storage key, over loopback HTTP endpoints beside `/mcp`. The leases live with its MCP session, are visible to every client, are replaced on settings/folder/key changes, and are restored after a restart. A log’s recorded team wins; the most specific live lease supplies a missing team before the configured default. Registration is not a tool: the person decides which directories the server may read. The Origin gate stays, registration is refused off loopback, and the key stays in memory with precedence over the file’s key while its lease lives.

   `connect` reads server configuration only from the home file or `--config`. It separately leases top-level `logdir` and `team` from its working directory’s `.wpilog-mcp.yaml`, together with its directory/team flags; an ignored project `servers` section is noted in the daemon log. Thus a project cannot define the shared server for everyone. The extension offers project YAML once, never overwrites it, and retires only recognized old entries in untracked/ignored `.mcp.json`. Tracked/custom entries stay with a note; the old daemon is stopped and its private settings removed.

   Updates flow one way: the standalone scripts may bootstrap the matching extension from an exact tag or the newest release including pre-releases; after that the extension updates the server and the Marketplace updates the extension. Both scripts prompt in a terminal and preserve settings. Explicit `--refresh` stops daemons and builds a fresh install beside a complete recovery backup. Automatic updates never refresh or install an extension. There is no operating-system service: clients start the server when needed, and `idle_exit_minutes` is the user’s policy in YAML (`0` by default). A different running version is replaced on the next `start` or `connect`.
6. **A bridge, for starting on demand and for clients that take only a command.** `wpilog-mcp connect <name>` is a small program in the same JAR: it makes sure the named daemon is running, starting it if not, then relays newline-delimited JSON-RPC between its standard streams and the daemon's `/mcp` endpoint, one session per bridge. Claude Code’s local registration is this bridge command at user scope, because a Claude Code started in a terminal with VS Code closed must start the server itself, which a URL cannot do, and one started beside the viewer must share its server, which VS Code's registry cannot offer to a process outside VS Code. `connect --url <url>` relays to any server without starting anything, for the clients whose configuration takes only a command (Claude Desktop's file is one), so they reach a pit server too.
7. **Bulk data has its own door, in Arrow's format.** Every sample of an entry is available from `GET /data/entries` on any server running the HTTP transport (§6), as an Apache Arrow IPC stream or as CSV, with the same `inputs` a tool result would carry. Arrow is the format that pandas, polars, DuckDB, and R read without parsing, which is what a script that analyzes the data wants; the server writes the stream on the heap with Arrow’s Flatbuffers format classes alone, never its allocator, so nothing in the server leaves the garbage collector's care (§6). MCP stays the channel for tools and their results; a tool never returns a hundred thousand samples as JSON, and a viewer never pages through ten thousand at a time. The viewer, an agent's script, and a dashboard read the same door.
8. **The webview's libraries are bundled as static assets, and chosen for taking Arrow.** The rule against runtime npm dependencies is about the Node side of the extension, which stays dependency-free; the webview bundles its libraries as files under `media/vendor/`, each with its license and its version pinned in the repository, not fetched at build. Because the data arrives as Arrow (decision 7), the libraries are ones that consume it without conversion: a time-series library that takes typed arrays for the panes (§5), and Perspective, which loads Arrow directly, for a data view (§4). The pane library is ours to drive; Perspective is used as it comes. The bytes are opened by a reader of our own (`media/arrowStream.js`, a few hundred lines for the subset the server writes, parsing the Flatbuffers by hand from the format's definitions) rather than Arrow's JavaScript library, which is several megabytes for what amounts to two columns of numbers; the reader runs under Node too, where it is checked against the server's streams that pyarrow has read, and refuses anything outside the subset rather than misreading it. Arrow's library can replace it the day the data view needs the whole format.
9. **Opening a log opens the explorer.** The read-only custom editor handles `*.wpilog`; a REV companion opens through its wpilog. A standalone `.revlog` editor remains planned. “Open With” keeps other editors available. Viewing does not write files; the explicit organizing choices in §9 do.
10. **The log folder can be a store, by the person's choice.** The layout the pit server owns ([PIT_SERVER_PLAN.md](PIT_SERVER_PLAN.md) §11) is not the pit server's alone: any server can keep a store, and the extension offers to turn the configured log directory into one and to organize the files already in it. It offers; it never reorganizes a folder unasked. Once the folder is a store, the rules of that plan hold here: files enter by import, a file dropped in by hand is reported and the extension offers to import it, there is no automatic retention deletion, and imports preserve original names and provenance (moves remove their verified source copy).

### 2. Layout and wiring

Everything is under `vscode-extension/`, in the layout the extension has:

| Path | What it holds |
|---|---|
| `package.json` | Gains the custom editor, the views container and views, the explorer's commands (`wpilog-mcp.explorer.*`), and the pit server URL setting, with `order` values the manifest test pins |
| `src/extension.ts`, `src/explorer.ts` | The glue: `extension.ts` wires the explorer in beside the servers; `explorer.ts` holds the clients, the views, the editor provider, and the commands (the URI handler comes with the charts) |
| `src/explorer/*.ts` | Pure modules: the MCP messages, the tree models, the editor page, and later the request planner for the plot, the chart specification, the prompt builder, CSV formatting |
| `src/mcpClient.ts`, `src/dataClient.ts` | The MCP client over HTTP (§3), and the data endpoint client that fetches an Arrow stream and hands its bytes to the webview |
| `media/vendor/` | The bundled libraries, each with its license: uPlot today; Perspective’s engine and viewer when that milestone lands |
| `media/` | The webview: its HTML, CSS, scripts, and the bundled charting library with its license; `.vscodeignore` keeps it in the package |
| `src/test/` | The tests, run by `npm test` as today |

Nothing changes in Gradle, CI, or the release workflow: the one extension they build, test, and publish is the one that grows. `doc/DEVELOPMENT.md` describes the viewer's modules and the real-VS-Code test (§10) in its extension sections, and `vscode-extension/README.md` describes the viewer beside the assistant setup.

### 3. The clients in the extension host

**The server process.** The extension runs the installed launcher’s `start http --config <home file>`. `start` is idempotent, replaces a different running version, and records the port in `~/.wpilog-mcp/run/http.pid`. Permanent settings, including the port and optional idle exit, belong to YAML. The extension does not write a daemon configuration or choose a port; a stranger on that port is an explained refusal. Startup retries use backoff; the log/restart commands act on the shared daemon.

**The MCP server definition.** VS Code’s agents get one HTTP definition after the window’s registration succeeds. Claude Code gets one user-scope `connect http` registration. Project directories come from the bridge’s flags or project YAML; per-project `.mcp.json` entries are retired under the migration rules in decision 5.

**One server, with leased directories (milestone 7).** The extension’s own MCP session registers User and open-project roots with their teams and secret-storage key. A 30-second ping preserves the session without changing lease precedence; a lost session is initialized and registered again. Updating settings, the key, or folders replaces the lease without a daemon restart. The dynamic validator, listing, store discovery, and inbox watcher share the live directory set. The Logs tree shows `configured` or `leased` origins.

**The MCP client.** `initialize`, then `tools/call` over `POST /mcp` with the `Mcp-Session-Id` header, which the extension host can read where a browser could not; a tool's result is the parsed JSON of its text content, and `isError` becomes a rejected promise. Requests run in parallel, which the HTTP transport supports. The planned pit-server connection will use the same client protocol.

**The data client.** `GET /data/entries` (§6) for the samples of one or more entries over a window, read as a stream of bytes and handed to the webview as a transferable buffer, where the bundled reader opens record batches as typed arrays (an `int64` timestamp column becomes a `BigInt64Array`, which the webview converts once to seconds in a `Float64Array`; values arrive as `Float64Array`). The extension host parses nothing; it moves bytes. It sends `If-None-Match` with the tag of the last response for the same request, so a window the viewer returns to costs one round trip and no bytes.

### 4. Views

- **Logs**: a tree in an activity bar container "WPILog Explorer", from `list_available_logs`. In a plain directory, grouped by event and then by date, showing the friendly name, the match, and the size. In a store (§9), grouped by robot and then by session, each session showing its files (the robot's log, its REV logs, a capture, the system logs) and its event and match, with files the listing reports as unmanaged in a group of their own that offers to import them. A filter box narrows by name, event, and match. With a pit server URL set, a second root lists its sessions from `list_available_logs`, newest first, with the robot's name, whether it is open, and whether the mirror holds it (pit server plan §11). Right-click: open, reveal in the file explorer, copy path, pin or unpin on the pit server.
- **Entries**: a tree for the active log, from `list_entries` and `get_entry_info`: name, type, sample count, with struct fields and array elements as children from `numeric_leaf_paths`, and a filter box with the same pattern `list_entries` takes. Click plots the entry in the active pane; drag adds it to another.
- **The editor**: one webview per open log, in the editor area, with:
  - a **timeline** across the top, the whole log, with phases from `get_match_phases` shaded (autonomous, teleop, test, disabled) and the Driver Station timeline's events as marks (`get_ds_timeline`: brownouts, enable and disable, alerts), where a drag selects the window the panes show;
  - **plot panes**, one or several, each with any number of entries, time on the x axis in seconds from the log's start, a shared cursor across panes with a readout of each series' value at the cursor, zoom and pan with the wheel and the keyboard, and a step drawing for entries whose sampling the server classes as change-only, never a line through a hold;
  - a **statistics panel** for the selected series over the visible window or the selection, from `get_statistics`: count, min, max, mean, median, standard deviation, the quartiles, and `data_quality` with its reasons, shown as the server states them, with the confidence level and never a verdict;
  - a **console pane**, from `search_strings`: a pattern, a level filter, collapsed repeats, each match with its time, where clicking a line moves the cursor to it and matches in the window are marked on the timeline;
  - a **REV pane**, from `list_revlog_signals` and `get_revlog_data`: the signals by device, each with its synchronization method and confidence, plotted on the robot's clock in the same panes as the log's entries, with the offset shown and a note when a REV log is not synchronized;
  - a **field view**, when the log has a robot pose the signal resolver finds or the user picks: a top-down plot of the pose over the window on an outline drawn from the bundled game data's field geometry (length, width, zones), with no field image, since none is bundled;
  - a **data view**, a `<perspective-viewer>` fed the same Arrow bytes the panes draw from: a grid of the selected entries' samples with filtering, sorting, grouping, and pivots, Perspective's own charts for a quick scatter or histogram, and export to CSV, all from the library as it comes, for the exploration a person does before deciding what to plot. In follow mode (§8) each batch is appended to its table, so the grid tails the session. The view is the library's, so its charts carry none of the panes' conventions (phases, steps, the shared cursor); the panes stay the place for a time series.
- **Status**: the viewer's server state in the status bar (starting, ready, restarting), and for a pit server its reachability and the mirror's age, as the pit server plan's extension section specifies.

### 5. The plot and its data

**Resolution.** The viewer draws from every sample where it can. For each series it fetches the whole log's samples from the data endpoint (§6) as typed arrays, up to a budget per series (default four million samples, about 64 MB of timestamps and values), and keeps them in the webview; zoom and pan then touch no server, the cursor reads the exact sample under it, and a spike one sample wide is drawn where it is. Drawing reduces the samples to the pane's pixels in the webview, by the minimum and maximum per pixel column, which keeps every extreme and is a pass over a typed array, fast enough to run on every frame. A 50 Hz entry over a ten-minute shop session is thirty thousand samples; a 1 kHz entry over an hour is 3.6 million, still within the budget.

Beyond the budget, the data endpoint buckets (`max_points`, the same semantics as `read_entry`'s), and the viewer fetches the visible window at a few times the pane's width on each zoom and pan after a short debounce, drawing a bucketed response as a band (minimum to maximum) with the mean as the line, the readout saying the cursor is on a bucket and giving its range, and refetching at full resolution once the window fits the budget. Either way an exact series is drawn as points joined by lines, or by steps for change-only sampling.

**The library.** uPlot (MIT, about 50 KB, canvas, built for large time series) is bundled: it draws steps, bands, multiple y axes, and a synchronized cursor across panes, and it has no dependencies. It is bundled under `media/vendor/` with its license file; the webview's content security policy allows scripts only from the extension's own resources by nonce, and no remote content. The field view and the timeline are drawn directly on a canvas, which is simpler than bending a plotting library to them.

**Theme.** Colors come from VS Code's theme variables, so the viewer follows light, dark, and high contrast themes; series colors are a fixed palette chosen to stay distinct on both backgrounds, with the phase shading at low opacity behind.

**Time.** The x axis is the log's own seconds, as every tool reports time, so a value a person reads off the plot is the value they would pass to a tool. Where the log carries wall-clock time (`systemTime`), a toggle labels the axis with it as well (not yet).

### 6. Server additions

Two tools, one endpoint, and the daemon's new verbs.

**The daemon's verbs.** `connect <name> [--config <path>]` or `connect --url <url>`, the bridge of decision 6: with a name it ensures the daemon as `start` does, with a URL it starts nothing; either way it opens an MCP session over HTTP and relays. Each line from standard input is posted to `/mcp` with the session header; the response body, when there is one, is written as one line to standard output; a notification's `202` writes nothing; the server's own messages, which the HTTP transport would send on its `GET` stream, are written as they arrive (the transport sends none today, only keep-alives, so the relay is exercised by a test server; the bridge is ready for the day the server has notifications to send). The bridge ends when its input closes, and deletes its session so the daemon's idle clock can run. The stop token lives in `~/.wpilog-mcp/run/<name>.token`, readable by the user alone, and reaches the daemon in its environment, never on its command line. `stop <name>` asks the daemon to finish calls in progress and exit, by a loopback-only request authenticated with its stop token. The daemon gains the idle exit and the version in `/health`, and `start` the restart on a version mismatch. All of it in `Main` and `DaemonManager`, documented in `doc/STANDALONE.md`, where `stop` replaces the advice to kill the process.

 The tools go through the tool checklist in `doc/DEVELOPMENT.md`, are documented in `doc/TOOLS.md`, called in the responses scenarios file, and added to the stress tests; the endpoint is documented in `doc/STANDALONE.md` beside the HTTP transport and checked by the same claim checks against real responses.

**The data endpoint.** `GET /data/entries`, served by the HTTP transport beside `/mcp` and `/health`, with query parameters `path` (the log, validated as every tool's path is), `names` (one or more entries or field paths, comma separated), `start_time` and `end_time` (seconds, as the tools take them), `max_points` (optional; without it, every sample), and `format`: `arrow` (the default) or `csv`. The response is the samples of each named entry over the window, independently timestamped, since entries are not aligned and aligning them is the reader's choice.

- **`arrow`** is the Apache Arrow IPC streaming format, `application/vnd.apache.arrow.stream`: a schema message, then record batches, then the end-of-stream marker. One stream carries one table per named entry, as a sequence of batches each tagged with the entry in its custom metadata; a reader that wants one entry filters by that tag, and a reader that wants a frame per entry splits on it. Each entry's table has a `timestamp` column of Arrow's `Timestamp(MICROSECOND)` type, exact as the log stores it, and a `value` column typed by the entry: `Float64`, `Int64`, `Boolean`, a `Struct` with the schema's fields for a struct entry, a `List` of the element type for an array, and `Utf8` for a string entry, so text is in the stream too. A stream has one schema, so the entries in one request share a value type (several doubles, say; a bucketed request needs only numeric entries, since every bucket has one shape); entries of different types are requested separately, which the viewer does anyway, one request per series. A bucketed entry (`max_points`) has `count`, `min`, `max`, `mean`, `first`, and `last` columns, with `mean` null where a bucket holds no finite sample, as the project's rule on uncomputable values requires. The schema's metadata carries what a tool result would: the server version, `inputs` (the log, the entries, the window, the file's size and modification time), the time range, and per entry its sampling class (periodic, change-only, event), the unit its name states where it states one, its decoded sample count, original record count, and any decode problem with the tools’ warning text. Responses are written in batches; decoded entry values may remain cached in server memory.
- **How the server writes it.** With Arrow's format classes alone (`arrow-format`, the generated Flatbuffers for the schema and batch headers, and the small Flatbuffers runtime), on the heap: the server lays out each batch's validity bitmaps, offsets, and data buffers in byte arrays, pads them to eight bytes as the format requires, and writes the encapsulated messages. It does not use `arrow-vector` or `arrow-memory`, whose off-heap allocator, reference counting, and `Unsafe` dependence would put memory outside the heap the cache and the `maxHeap` setting govern and outside the garbage collector's care. The writer is a few hundred lines with a test against the specification and a cross-check against the reference reader (§10); the full library stays available if the writer proves fiddlier than the specification suggests.
- **`csv`** is one table per entry, `timestamp_sec,value` with a header line, concatenated with a blank line and a `# entry: <name>` comment between, the form the existing CSV export writes, so a script written for one reads the other.
- **Limits and errors.** A response is capped by a configured size (default 512 MB); a request over the cap is refused with a JSON body that gives the count, the size, and the hint to narrow the window or pass `max_points`, never silently cut. A missing entry is an error naming it, as a tool would. A file that changes during the stream is handled as a tool call is: the stream ends early, with a final empty batch whose metadata says the file changed, and the reader discards what it received.
- **Caching.** `ETag` includes the file snapshot and query, plus each requested REV source and its synchronization state. An unchanged request returns `304`; changing a REV offset invalidates it.
- **Who reads it.** The viewer, through its data client. An agent with shell access, by `curl` against the URL that `get_server_guide` reports under `data_endpoint` whenever the transport is HTTP, which gives a script every sample of an entry in one request; on a stdio server there is no endpoint, and the CSV export tool stays the way. A notebook or a script: `pyarrow.ipc.open_stream` on the response, or `polars.read_ipc_stream`, gives a data frame in one line, with the timestamps as timestamps and the struct fields as columns. A dashboard: this is the query endpoint the pit server plan leaves for Grafana (its §12), with `format=csv` or a `json` format added when Grafana's data source plugin asks for one.
- **Security.** The endpoint reads; it writes nothing. It is behind the `Origin` check, so no web page can fetch it, and behind the path validator, so it serves only files in the configured log directories; on the pit server it is under decision 7 of that plan, behind a team's proxy when they add one.

**`read_entry` at screen resolution.** For the assistant, which reads through MCP and cannot take an Arrow stream: a new optional parameter `max_points`. When the samples in the window number no more than it, the result is as today, exact. When they do, the window is divided into that many buckets of equal duration, and each bucket with samples returns `timestamp_sec` (its start), `count`, `min`, `max`, `mean`, `first`, and `last`; the result says `bucketed: true` with `bucket_sec`, and `total_in_range` stays the true count. The extremes are kept because a spike that a mean would hide is the thing a person is looking for. For a change-only entry, `first` and `last` let the viewer draw the holds correctly across a bucket. Struct fields and array elements go through the field paths as the exact read does; a non-numeric entry is read exactly and `max_points` is reported in `skipped` with the reason. The differential check recomputes `min`, `max`, and `mean` per bucket from the raw records of the entry the result names.

**`render_chart`.** Takes what `read_entry` takes, plus `entries[]` for several series, a `kind` (`time_series`, `histogram`, `scatter`, `field`), and a `width` and `height`. Returns MCP image content (a PNG drawn with the JDK's headless imaging and written by `ImageIO`, with no dependency; skipped with a note where the runtime lacks the headless toolkit), the chart specification as JSON (series, axes with units from the names, the phases, the window), and the numeric summary of what was drawn (per series the count, min, max, mean, and the window) with `inputs`, so a model that describes the chart describes numbers the tool returned. A change-only series is drawn as steps; the phases come from the Driver Station data; axes carry the unit the name states and nothing the name does not. The specification is what the explorer draws from, so the picture the assistant gets and the picture a person sees come from the same description; the specification carries a `vscode://TripleHelixProgramming.wpilog-analyzer/open?...` link that the extension's URI handler opens as the same chart, interactive, when the extension is installed.

### 7. Looking to asking, and to a notebook

**A notebook.** "Open in notebook" (`wpilog-mcp.explorer.openInNotebook`) writes a notebook beside the log, or into the workspace, with three cells: one that reads the current log's selected entries over the window from the data endpoint into a data frame (`pyarrow.ipc.open_stream` on the URL, with the polars line in a comment), one that plots them, and a markdown cell that names the log, the entries, the window, and the server's `inputs`, so the notebook says where its numbers came from. VS Code opens it with its own notebook editor, and the person has the scientific stack from there, which the extension neither bundles nor needs: if Python or Jupyter is missing, VS Code says so when the cell runs, and the notebook is still a record of what was selected. The data is already in the format those tools read, so this is a few lines of generated text, and it is the whole answer for anyone who wants analysis beyond what the tools do.

**A prompt.** The editor offers "Ask about this selection": the current log's path, the selected entries, the window or selection, and the pane's kind become a prompt that names them and the tool the assistant would call first, and the prompt opens in the chat the user has. VS Code's own chat accepts a prefilled query through `workbench.action.chat.open`; for other assistants the prompt is copied to the clipboard with a message saying so. Which assistants can be opened with a prompt is an open question (§12); the clipboard always works. With no assistant configured, the command still produces the prompt, and the viewer is complete without it.

### 8. Pit server and live sessions

With `wpilog-mcp.pitServerUrl` set (the pit server plan's setting), the Logs view lists the pit server's sessions and the editor opens one by path through the pit server's tools, as it opens a local log through the local server's. An open session has a **follow** toggle: the window tracks the latest time, and the data client fetches each visible series from the last timestamp it holds, once a second, from the data endpoint, appending to the typed arrays in the webview; the console pane pages `search_strings` from the last completed boundary without collapsing repeats and retains the latest 500 matches. Follow runs while the editor is visible. Mirrored sessions (pit server plan §11) open from the mirror when the pit server is unreachable, and the editor says which copy it is reading. Nothing here subscribes to the robot: the pit server is the one listener, by its own decision 6.

### 9. Organizing the log folder

**The offer.** When the configured log directory is not a store and holds log files, the extension offers once, through a notification with the count: organize these files by robot and session? The choices are yes, not now, and never for this folder, the last remembered in the extension's global storage. The same offer comes from a command (`wpilog-mcp.explorer.organizeLogs`) at any time, and, once the folder is a store, whenever the listing reports unmanaged files in it (a USB stick's worth dragged in), with the count and the names. Nothing happens without a yes.

**What a yes does.** The server makes the directory a store (`store.json`) and imports every log file in it through the import pipeline the pit server plan specifies (§11 there): classified by content, hashed, read for a logged serial, its time range, `systemTime`, and the event and match from its Driver Station entries, then moved, not copied, into its place, since the folder is the person's own and the point is the organization; the original path and name go into the session's manifest. A REV log lands in the session of the wpilog it synchronizes with, by the existing synchronization. A file the store already holds by hash is left where it is and reported. The import runs inside the server that owns the store, the laptop's one daemon (decision 5), through `POST /store/import` with the paths and a `move` flag, which returns a job the extension polls for progress; the `import` command of the pit server plan posts to a running daemon the same way and does the work itself only when none is running, so the store never has two writers. Additional log directories stay plain directories, and their files can be imported into the store by copy from the Logs tree.

**Which robot.** Most files copied by hand carry no serial. The import asks the extension, and the extension asks the person, once per batch: a quick pick of the robots the store knows, or a new one by name. A name is an identity basis of its own, `stated`, beside `logged` and `device` in the pit server plan's §8.5; a robot known only by name has its directory under `robots/` by that name until a file logs a serial, when the manifest records the serial and the server renames the directory, as it renames one known by address. When a stated robot's file logs a serial that already names another robot's directory, the listing reports the two as one robot and the extension offers a merge; the server never merges on its own. A batch the person declines to assign waits under `unassigned/`, where the listing shows it, and is assigned later from the tree.

**What does not change.** A file keeps its name, under its session's `robot/` directory, so a name someone knows still finds it, and a path someone wrote down in a conversation is answered by the listing's `moved_to` note for a few days after the import. The session directory's name is the convention the pit server's captures follow, so a person reading the folder learns the layout the pit server will fill, and a mirror of the pit server (§8) beside the store reads the same way. The explorer's trees show both stores alike.

### 12. Open questions

- **Decided by the maintainer:** `POST /store/import` admits source paths only inside configured log directories, as the Java importer does. A USB stick or any other outside path goes through the inbox. A move-anything write surface on a server with no authentication is not acceptable; the inbox is a folder the user owns.
- Whether `render_chart`'s specification (§6) should be Vega-Lite rather than a form of the server's own. Vega-Lite is a standard that assistants understand natively, which would let an assistant read a chart and ask for one in the same language, and the webview could render it with the Vega library. The server, which draws the PNG with the JDK, cannot execute Vega, so the choice is between a specification of our own with a documented mapping to Vega-Lite, and Vega-Lite as the specification with the PNG drawn from the subset the server supports. Not decided; the first charts will show which subset matters.
- **Decided for milestone 7:** registration is an HTTP endpoint for the extension and bridge, never a tool: which directories the server may read is the person's decision, and a model that wants another folder asks the person to add it.
- **Decided for milestone 7:** the TBA key may be registered in memory over loopback with the extension's lease, or kept in `servers.yaml` by the user. Both are supported, with the registration winning while it lives, since a key in memory is the only way the extension's secret-storage key reaches a server it does not configure.
- **Decided in milestone 7:** idle policy is `idle_exit_minutes` in permanent YAML, applies to any background HTTP daemon, and defaults to zero. The extension no longer writes its own idle policy.
- Decided for organizing (§9): move is the default, with copy offered explicitly before import. Moving organizes in place and keeps one copy; provenance retains the original path. Copy leaves the originals and the store reports them as unmanaged, without immediately repeating the same offer.
- Which assistants accept a prefilled prompt (§7). VS Code's chat does through its command; whether the Claude Code extension exposes an equivalent, and what Cursor's is, are to be checked, with the clipboard as the floor.
- **Implemented:** Arrow is written at the format level, with struct/list metadata guarded by the independent test reader, the extension reader, and the pyarrow CI cross-check.
- uPlot against drawing on a canvas directly for the plot panes (§5). The library's cursor, bands, and axes are a lot to rewrite; a hand-drawn plot would be smaller and entirely ours. The proposal is the library, revisited if its bundle or its API gets in the way.
- Whether the custom editor should claim `.revlog` on its own, or only open one beside its wpilog (§1, decision 9). The proposal claims both and shows a REV log alone with its signals on its own clock, marked as not synchronized.
- How much of the pit server's live data belongs here (§8) against in the pit server's own future web view. The proposal is follow and the console only, with the latest values and `wait_for_change` left to the assistant.
